### C5 caveats

The classical ablation (`lib/vqc_classical.py`) uses `n_qubits -> hidden -> 1`
(ReLU hidden, tanh output rescaled to the gate VQC's [-1, 1] PauliZ range).
`hidden` is chosen so the parameter count is close to the gate VQC's
`n_layers * n_qubits * 2` rotation angles, but the two architectures are not
directly parameter-comparable. The C5 comparison is therefore "similarly sized
classical block", not an exact parameter match. Its n=15 signal was not
statistically significant (see [Statistical Significance](#statistical-significance)).

## Strategy and Key Decisions

### Protocol assumptions

The paper leaves several protocol details unspecified. The choices made here:

- **Epoch-count assumption**: 30 epochs. The paper does not specify an epoch
  count. Loss-curve sanity check: mean batch loss 0.41 -> 0.10 over 30 epochs
  on the ~786-row balanced training pool (reasonably converged). Optimizer
  Adam, lr=1e-3, batch size 32. The epoch count could under- or over-train the
  GQC secondary expert relative to the paper's unknown setting (listed as a
  confounder in [Diagnosing the Reproduction Gap](#diagnosing-the-reproduction-gap)).
- **Autoencoder architecture**: `input_dim(29) -> 256 -> 128 -> 64 -> 6 -> 64
  -> 128 -> 256 -> input_dim` (encoder/decoder mirrored, ReLU hidden, linear
  output), latent dim 6 matching the VQC's qubit count. See
  `lib/autoencoder.py`.
- **XGBoost hyperparameters** (primary expert and router): `n_estimators=200,
  max_depth=4`. The paper does not specify them. A probed alternative
  (`n_estimators=1000, max_depth=8`, early-stopped) raises baseline AUCPR from
  ~0.71 to ~0.74 on a 3-split sample. It was not adopted for the
  paper-accurate n=15 runs, to keep one fixed hyperparameter set across the
  gate/photonic/classical comparison. It was later run at n=100 as
  `configs/moe_gate_tuned_xgboost_powered.json`.
- **Router training split**: the ANALYSIS split (see
  [Paper vs Reference Code Disagreements](#paper-vs-reference-code-disagreements)).
  The literal "validation" reading was also tested at n=100
  (`configs/moe_gate_validation_router_powered.json`) with no material change.
- **Temperature calibration**: one scalar temperature fitted with Adam (not
  LBFGS) by minimizing BCE on the validation split; see `lib/calibration.py`.
  Clamp floor history is in [Known Issues and Open Bugs](#known-issues-and-open-bugs).
- **CV protocol**: repeated stratified 5-fold CV, 3 repeats (the paper's
  protocol) = 15 fold-runs per configuration, seed 42. For each fold the
  sklearn "test" indices are split 50/25/25 (stratified) into validation /
  analysis / holdout. A `MinMaxScaler` is fit on the training pool only. The
  training pool is downsampled to 50/50 class balance (~786-788 rows);
  validation/analysis/holdout keep the natural class balance.

### Fair baseline plan

- Claimed advantage axis: classification quality (AUCPR / AP) under a fixed
  low-latency inference budget, with a precision/recall trade-off.
- Baseline: XGBoost alone (the paper's own primary expert), reproduced
  directly with identical CV protocol, preprocessing, and seeded folds.
- Metrics: AUCPR (mean±std, median), AP (mean±std, median), precision, recall,
  matching the paper's Tables 2-5.
- Caveat: the downsampled per-fold training set is tiny (~788 rows), so
  fold-to-fold variance may exceed the paper's reported std if the paper's
  downsampling was less aggressive or its hyperparameters differ.
- Added ablation (C5, `configs/moe_classical_ablation.json`): classical dense
  layer in place of the VQC inside the same pipeline.

### Key decisions (2026-09-01)

- Chose the OpenML mirror over a Kaggle download: Kaggle needs an account/API
  key; OpenML is public and verified identical (same instance/class counts).
- C3 hardware-latency numbers (Table 6, "7-21 min overhead vs 12h
  fully-quantum") require OQC Toshiko QPU access, which is unavailable. The
  routing-fraction mechanism is reproduced instead; it is fully testable in
  software and, combined with any per-sample quantum latency, determines the
  overhead. Any extrapolated wall-clock is to be labeled simulator-derived.
- C4 (Table 1 latency benchmark) was first deprioritized as disconnected from
  the MoE headline claim and mistakenly grouped with Table 6 as
  hardware-blocked. Correction: Table 1 is a CPU-only benchmark per the
  paper's own text, and it was implemented and run the same day
  (`outdir/run_20260901-160921/`). See
  [Latency Benchmark (C4/Table 1) Results](#latency-benchmark-c4table-1-results).
- No original code repository exists: the paper does not link one. Framework
  versions in the paper: PennyLane 0.41.1, PyTorch 2.7.0, NumPy 1.26.4. This
  reproduction used later versions (e.g. PennyLane 0.45.1, xgboost 3.4.1,
  merlinquantum 0.4.1, scikit-learn 1.9.0). No pretrained weights; everything
  trains from scratch.

## MerLin API Notes

- Tested against `merlinquantum==0.4.1`, which differs from the 0.3.2 API in
  two places:
  - `ml.MeasurementStrategy.PROBABILITIES` is deprecated; use
    `ml.MeasurementStrategy.probs(computation_space)` instead.
  - `ml.LexGrouping(output_size, num_classes)` (0.3.2 keyword names) became
    `ml.LexGrouping(input_size=..., output_size=...)` in 0.4.1. Pass the
    upstream quantum layer's `output_size` explicitly as `input_size`.
- Photonic VQC design (`lib/vqc_photonic.py`): 6 modes (= `n_qubits`, for
  comparability with the gate model), 3 photons (`spread_input_state` places
  them evenly, `[1,0,1,0,1,0]`), one trainable `add_entangling_layer` on
  either side of a single `add_angle_encoding` pass (matching the gate model's
  single data upload), `MeasurementStrategy.probs(UNBUNCHED)` (threshold
  detection) giving a `C(6,3)=20`-outcome probability vector, and
  `LexGrouping(20 -> 2)` reduced to a scalar fed into the same `Head` used by
  the gate branch.
- Hardware-aware record:

  | Field | Value |
  |---|---|
  | Computation space | UNBUNCHED |
  | Detector model | threshold |
  | Photon number | 3 |
  | Modes | 6 |
  | Input state | `[1,0,1,0,1,0]` |
  | Encoding | angle, all 6 modes, scale=1.0 |
  | Measurement strategy | `probs(UNBUNCHED)` |
  | Postselection | none |
  | Simulator | MerLin CPU analytic (shots=0) |

- `GQCModel` (`lib/gqc_model.py`) takes `cfg["model"]["backend"] in
  {"gate", "photonic", "classical"}` and shares the identical autoencoder,
  head, training loop, calibration, and MoE code across all three, so metric
  differences are attributable to the swapped block alone.
- A trainable-readout photonic variant (replacing the fixed `LexGrouping`)
  was run at n=100 as `configs/moe_photonic_trainable_powered.json`; see
  [Powered Re-Run Write-Up](#powered-re-run-write-up).

## Diagnosing the Reproduction Gap

Gate-model paper-accurate run (`configs/moe_gate_original.json`, 3x5 CV = 15
splits, 30 epochs). Full table in `outdir/run_20260901-122850/metrics_table.csv`.

| Row | AUCPR mean±std | AP mean±std | Precision mean±std | Recall mean±std | Routed frac mean |
|---|---|---|---|---|---|
| XGBoost baseline | 0.700±0.091 | 0.705±0.090 | 0.083±0.064 | 0.936±0.052 | 0.0 |
| MoE γ=0.5 | 0.692±0.087 | 0.697±0.085 | 0.128±0.148 | 0.920±0.065 | 0.016 |
| MoE γ=0.6 | 0.694±0.088 | 0.699±0.086 | 0.128±0.152 | 0.923±0.066 | 0.014 |
| MoE γ=0.7 | 0.696±0.088 | 0.701±0.086 | 0.131±0.151 | 0.923±0.066 | 0.013 |
| MoE γ=0.8 | 0.702±0.092 | 0.706±0.090 | 0.128±0.151 | 0.923±0.066 | 0.011 |
| MoE γ=0.9 | 0.701±0.087 | 0.706±0.085 | 0.126±0.152 | 0.925±0.068 | 0.009 |

Paper (Tables 2-5): XGBoost AUCPR 0.78±0.10 / AP 0.770±0.096 / Precision
0.081±0.059 / Recall 0.934±0.051; best MoE (γ=0.6) AUCPR 0.79±0.09 / AP
0.793±0.085 / Precision 0.122±0.133 / Recall 0.913±0.053.

**Observed gap.** AUCPR/AP absolute levels sit ~0.08 below the paper's for
BOTH XGBoost and MoE, but the shape of the comparison is largely preserved:

- (a) fold-to-fold std is close to the paper's (0.087-0.092 here vs 0.08-0.11);
- (b) precision is higher for every MoE threshold than for XGBoost alone
  (0.126-0.131 vs 0.083), matching the paper's direction and magnitude
  (0.122 vs 0.081);
- (c) routed fraction at γ=0.5 (1.6%) and γ=0.9 (0.9%) falls inside the
  paper's reported "worst case ~3% at 0.5, best case ~1% at 0.9" range;
- (d) XGBoost recall (0.936) essentially matches the paper's (0.934).

**What does not reproduce cleanly.** The paper's central AUCPR/AP claim, that
MoE at γ≈0.6-0.7 exceeds XGBoost, does not clearly hold. The best threshold
here (γ=0.8, AUCPR 0.7016) beats the baseline (0.7004) by only 0.0012, deep
inside one fold-to-fold std (~0.09); at γ=0.5-0.7 MoE is below the baseline.
The paper's own reported gain is also small (0.79 vs 0.78, ≈0.01, inside its
own std of ~0.09-0.10), so at n=15 both results read as a same-order,
statistically fragile, threshold-dependent effect, but this reproduction's
central estimate does not clearly land on the same (higher) side.

**Root-cause exploration.** The paper does not specify XGBoost
hyperparameters. A 3-split probe found XGBoost mean AUCPR rises from 0.71
(`n_estimators=200, max_depth=4`, the default here) to 0.72 (500/6,
early-stopped on validation) to 0.74 (1000/8, early-stopped). XGBoost capacity
and early stopping are a material lever on this ~786-row balanced training
set and likely explain a good part of the ~0.08 absolute gap without fully
closing it. The full 15-split pipeline was not rerun with these settings at
this stage, because XGBoost is also the MoE primary expert and the change
shifts both sides together. The tuned setting was later run at n=100 (baseline
mean 0.7255). This is labeled an **unresolved absolute-level gap** caused by
underspecified XGBoost hyperparameters, while the precision/recall trade-off
(C2) and routing fraction (C3) reproduce with reasonable fidelity.

**Confounders considered.**

1. The tiny ~786-row balanced training pool makes every downstream estimate
   (autoencoder, VQC, head, XGBoost) high-variance, at the same order as the
   paper's own reported std, so not obviously an implementation artifact.
2. The epoch count (30, an assumption) could under/over-train the GQC
   secondary expert.
3. XGBoost/router hyperparameters are unspecified (addressed above).
4. The router trains on the ANALYSIS split, per the paper's described
   procedure rather than its prose (see
   [Paper vs Reference Code Disagreements](#paper-vs-reference-code-disagreements)).

## Photonic and Classical-Ablation Results

All three backends (`gate`, `photonic`, `classical`) share the identical
autoencoder, head, training loop, calibration, MoE router, and CV protocol
(`configs/moe_gate_original.json`, `configs/moe_merlin_photonic.json`,
`configs/moe_classical_ablation.json`; all 3x5 CV, 30 epochs, seed 42,
identical XGBoost hyperparameters). Only the quantum/classical block differs.
XGBoost-baseline numbers are identical across all three runs (same seeded
folds): AUCPR 0.700±0.091, AP 0.705±0.090.

| Backend | AUCPR @ γ=0.6 | AUCPR @ γ=0.8 (gate's best) | AP @ γ=0.6 | Routed frac @ γ=0.6 |
|---|---|---|---|---|
| gate (PennyLane, original) | 0.694±0.088 | 0.702±0.092 | 0.699±0.086 | 0.014 |
| photonic (MerLin) | 0.665±0.132 | 0.672±0.122 | 0.669±0.131 | 0.021 |
| classical (ablation) | 0.690±0.085 | 0.690±0.085 | 0.693±0.085 | 0.019 |
| XGBoost baseline | 0.700±0.091 (no threshold) | | 0.705±0.090 | 0.0 |

Full per-threshold tables: `outdir/run_20260901-122850/metrics_table.csv`
(gate), `outdir/run_20260901-123922/metrics_table.csv` (photonic),
`outdir/run_20260901-124500/metrics_table.csv` (classical).

**Interpretation (after paired significance testing).** The point-estimate
ranking is gate ⪆ XGBoost > classical > photonic, but a paired t-test across
the 15 folds finds none of these pairwise differences significant (all
p > 0.18). What the ranking supports, weakly:

1. A suggestive, non-significant trend that the gate-model quantum block
   contributes something beyond a same-sized classical block (C5): the
   classical ablation never exceeds the baseline at any threshold, while the
   gate model marginally does at γ=0.8-0.9.
2. A suggestive, non-significant trend that this photonic circuit (one mesh
   either side of one angle-encoding pass, fixed non-trainable `LexGrouping`
   readout) underperforms the gate model (C6). It is directionally consistent
   across all 5 thresholds, which is modestly more convincing than any single
   p-value, but it is not a confirmed negative result.

The hypothesis at this stage was that a trainable readout would be the main
lever for the photonic branch (`scale=1.0` mirrors the gate model's angle
convention, so encoding scale was not an obvious miscalibration). That
hypothesis was later tested at n=100 and rejected; see
[Powered Re-Run Write-Up](#powered-re-run-write-up).

## Statistical Significance

The first write-up compared aggregate means against fold-to-fold std. That is
not a significance test: MoE and XGBoost are evaluated on the SAME 15 folds
(paired data), and it does not quantify power. Corrected analysis: for each
backend and router threshold, the paired per-fold difference
`(MoE_aucpr - XGBoost_aucpr)` across the 15 splits, a paired t-test, a
Wilcoxon signed-rank test, and a minimum-detectable-effect (MDE) calculation
(80% power, α=0.05 two-sided).

| Backend | γ | mean diff | paired-t p | Wilcoxon p | wins/15 | MDE (n=15) | folds needed for paper's ~0.01 effect @80% power |
|---|---|---:|---:|---:|---:|---:|---:|
| gate | 0.6 | -0.0065 | 0.404 | 0.638 | 10/15 | 0.021 | 67 |
| gate | 0.8 | +0.0012 | 0.697 | 0.433 | 9/15 | 0.021 | 67 |
| photonic | 0.6 | -0.0350 | 0.194 | 0.221 | 7/15 | 0.072 | 776 |
| classical | 0.6 | -0.0105 | 0.549 | 0.847 | 7/15 | 0.048 | 344 |

**None of the differences reach significance at n=15** (all p > 0.18).
Win-rate hovers near 50% for the gate model (9-11/15 across thresholds,
indistinguishable from a coin flip) and leans below 50% for
photonic/classical (6-9/15) without reaching significance.

**Verdict correction.** Photonic and classical results were first described
as a "clear negative result". That overstated the evidence. The correct n=15
characterization: point estimates consistently lean negative, but the paired
test cannot distinguish this from noise. C1 at n=15 is likewise
**statistically underpowered to confirm or refute**, not "not reproduced".

**Power analysis.** Detecting an effect the size of the paper's own claimed
gain (~0.01 AUCPR at γ=0.6), given the observed fold-to-fold variance, at 80%
power needs ~67 paired folds for the gate model, over 4x the paper's own
15-fold (3x5) protocol. The paper's repeated-5-fold design is therefore very
plausibly underpowered for the effect it reports, independent of this
reproduction. This motivated the n=100 re-run below.

### Parallel Statistically-Powered Runs

The six configs were run as separate OS processes, orchestrated by
`utils/launch_powered_runs.sh`:

- XGBoost (primary expert and router) is built with `n_jobs=2` by default

  `cfg["model"]["xgboost"]["n_jobs"]`) rather than `-1`/all cores. With
  several experiment processes running at once, each XGBoost using every core
  would oversubscribe the CPU (the machine used had 14 cores); 2 threads per
  process keeps concurrent runs within the available cores.
- First attempt, all 6 concurrent, hit two problems: (1) a `run_dir`
  timestamp collision, where processes starting in the same wall-clock second
  land on the same `outdir/run_<timestamp>/` path and corrupt each other's
  `config_snapshot.json` / `run.log` / `metrics.json`; (2) out-of-memory and
  swap thrashing from 6 processes at ~2 GB RSS each on a ~7.5 GB machine.
- Second attempt: 3 concurrent with a distinct `--outdir` per config. Still
  thrashed memory (splits slowed from ~55-65 s to ~180 s).
- Final version: 2 concurrent per batch, 3 sequential batches, each config
  with its own `--outdir` (`outdir/<config_name>/run_<timestamp>/`). Ran
  cleanly at ~4.9 GB / 7.5 GB with minimal swap. The ~1.5-2 GB RSS per process
  is front-loaded in the first folds (library/JIT/device construction), not a
  per-fold leak.

threshold for the tuned-XGBoost variant and at 3/5 thresholds for the

### Calibration Instability Finding

The worst-affected folds correlate with the secondary (GQC) expert's fitted
temperature `t2` collapsing toward its clamp floor (`t2=0.0010` on the worst
fold, vs a typical `t2≈0.2-0.5`). `lib/calibration.py::fit_temperature`
originally clamped `t >= 1e-3`. Adam can drive `t` toward that floor on folds
where the validation-set logits are close to separable, a known Platt-scaling
failure mode on small or near-separable data (the GQC is trained on only ~786
examples). Once `t≈0.001`, `apply_temperature`'s `sigmoid(logits/t)`
saturates to near-binary (0 or 1) for almost any nonzero logit.

This happens even though the routed fraction on the worst folds is small
(1.4%-6.3% of holdout points). AUCPR/AP are ranking metrics over the WHOLE
holdout set, so a few confidently-wrong saturated probabilities in a severely
imbalanced holdout (0.17% fraud) distort the precision-recall curve enough to
crater aggregate AUCPR.

**Mitigation applied** (`lib/calibration.py`, 2026-09-01T17:37:45): the
temperature clamp floor was raised from `1e-3` to `0.1` (100x less
permissive). The two gate tables above were generated before this change. A
fresh process is required for the change to take effect, so which powered
runs used which floor is determined by start time; see
[Powered Re-Run Write-Up](#powered-re-run-write-up). Whether the floor change
is a faithful fix or a deviation matters: it tests whether the negative mean
effect is (a) a genuine property of the paper's Platt-scaling approach on
small folds, or (b) an artifact of an implementation default that was too
permissive. Both as-implemented (old floor) and post-fix results are
therefore reported. The [post-fix gate re-run](#post-fix-gate-re-run) shows
the floor change alone does not reverse the verdict.

## Latency Benchmark (C4/Table 1) Results

Implementation: `lib/latency_benchmark.py`, `tests/test_latency_benchmark.py`,
`configs/latency_benchmark.json`. Output:
`outdir/run_20260901-160921/latency_benchmark.json` (curated copy:
`results/latency_benchmark.json`, figure `results/fig_latency.png`).

**Protocol** (paper Section 2.1, "Motivation", checked against the paper
text): reduce the ULB dataset to 10,000 rows, 90/10 train-test split, balance
the training pool to 90 samples/class (180 rows), PCA(2) for the
2-qubit-restricted kernel methods (QMKL, GFM); GQC uses its own autoencoder
for dimensionality reduction. 5 timing runs of 10 internal repetitions each on
a fixed batch of 50 test samples; run 0 is a warm-up, excluded from the
reported statistics. The paper states this benchmark ran "exclusively in a
CPU environment running PennyLane 0.41.1, PyTorch 2.7.0, and NumPy 1.26.4",
so it is a pure-software benchmark and needs no QPU.

| Algorithm | Paper (ms/sample) | Paper CV% | Reproduced (ms/sample) | Reproduced CV% |
|---|---:|---:|---:|---:|
| QMKL | 123.9 ± 0.4 | 0.34 | 13.60 ± 5.80 | 42.6 |
| Genetic Feature Map (GFM) | 48.4 ± 0.2 | 0.39 | 4.13 ± 1.96 | 47.4 |
| GQC | 0.089 ± 0.004 | 4.25 | 1.376 ± 0.220 | 16.0 |

Paper's claimed speedup: GQC 542x faster than GFM, 1387x faster than QMKL.
**Reproduced speedup: GQC only 3.0x faster than GFM, 9.9x faster than QMKL.**
The ranking reproduces (QMKL slowest, GFM middle, GQC fastest, consistent with
the paper's explanation that QMKL evaluates 3 kernels per pair vs GFM's 1),
but the magnitude of GQC's advantage is off by roughly two orders of magnitude
on the ratio. The absolute latencies differ asymmetrically: QMKL/GFM here are
~9-12x *faster* than the paper's (13.6 ms vs 123.9 ms; 4.1 ms vs 48.4 ms),
while GQC is ~15x *slower* (1.376 ms vs 0.089 ms). The gap is not a uniform
hardware-speed offset; GQC specifically is disproportionately slow here.

**Assumptions/deviations** (full detail in the `lib/latency_benchmark.py`
module docstring):

1. The paper does not specify QMKL's 3-kernel combination weights (equal 1/3
   weighting used) or the exact feature-map ansatze for QMKL/GFM (3 distinct
   small 2-qubit PennyLane circuits for QMKL and 1 for GFM, reconstructed from
   prose).
2. The 10,000-row reduction keeps all 492 fraud rows plus a random non-fraud
   sample. A literal i.i.d. subsample of the 0.172%-fraud dataset would leave
   too few fraud rows to balance 90/class. This should not affect inference
   latency, which does not depend on class balance.

**Not diagnosed:** why GQC is disproportionately slow. GQC's VQC and the
QMKL/GFM kernel circuits all use PennyLane `default.qubit` (pure-Python) here,
so a device difference between the methods is not the explanation within this
reproduction. Untested candidates:

- (a) The paper may have used a faster backend (e.g. `lightning.qubit`) for
  GQC specifically. That would help GQC (one 6-qubit/6-layer circuit per
  batch) more than the kernel methods (many small 2-qubit circuits).
- (b) The GQC forward pass here goes through a full PyTorch `nn.Module`
  (autoencoder + `TorchLayer`-wrapped VQC + FNN head), with per-call
  Python/autograd overhead even under `torch.no_grad()`.
- (c) PennyLane version differences (paper 0.41.1, here 0.45.1) may have
  changed the relative overhead of small 2-qubit circuits vs a deeper
  6-qubit/6-layer circuit.

Bottom line: the ranking is reproduced and the claimed magnitude is not. None
of (a)-(c) is confirmed as the cause.

## Known Issues and Open Bugs

### Resolved

- **Calibration numerical overflow (cosmetic).** `lib/calibration.py::apply_temperature`
  computed `sigmoid(logits / t)` as `1/(1+exp(-logits/t))`. On one CV split
  of the classical-ablation run (repeat=2 fold=3, and identically repeat=2
  fold=4) this raised `RuntimeWarning: overflow encountered in exp`: a very
  small fitted `t` combined with a large-magnitude logit. Fixed by clipping
  `logits / t` to `[-30, 30]` before `exp()` (a no-op in float64, since the
  sigmoid already saturates inside that range). Re-running
  `configs/moe_classical_ablation.json` gave identical aggregated metrics
  (`outdir/run_20260901-124730` matches `outdir/run_20260901-124500` to
  displayed precision). The low AUCPR on that split (holdout AUCPR 0.6025 vs
  a 0.8295 baseline for the same split) is genuine model behavior, not a
  computation artifact.
- **Router training split** (validation vs analysis): no material change at
  n=100; see
  [Paper vs Reference Code Disagreements](#paper-vs-reference-code-disagreements).
- **Trainable photonic readout hypothesis**: rejected at n=100; the trainable
  readout is the worst backend tested (mean diff -0.048 to -0.060, all
  p<0.001, the only backend with ≤55% win-rate at every threshold).
- **Gate post-floor-fix re-run**: the floor change alone does not reverse the
  gate model's significant-negative n=100 verdict; see
  [Post-fix gate re-run](#post-fix-gate-re-run).
- **Youden's-J degenerate-threshold bug** (found 2026-09-01, fixed
  2026-09-02). Notes written on 2026-09-01 describe this bug as unfixed and
  call for a full 6-config re-run; that was superseded by the fix and the
  exact impact bound below.
  - Mechanism: `lib/moe.py::youden_j_threshold` picked `argmax(tpr - fpr)`
    over `sklearn.metrics.roc_curve`'s threshold array, which prepends a
    synthetic first threshold of `np.inf` for the trivial "reject everything"
    point (TPR=FPR=0, J=0). On folds where the secondary (GQC) expert's
    calibrated validation probabilities have no real threshold with J>0
    (plausible on a tiny, highly imbalanced validation split), the argmax can
    land on that point, giving `tau2=inf`. Then `p2_hat > tau2` is always
    `False`, so `build_router_targets` treats the secondary expert as correct
    only on true negatives and incorrect on every true positive for that
    fold, corrupting the router's training targets.
  - Observed: `tau2 in {inf, values > 1.0}` on 0-3/100 folds depending on
    config/backend. It correlates with large negative per-fold diffs on the
    affected fold (e.g. `moe_photonic_trainable_powered`'s one degenerate-tau2
    fold has diff=-0.31, vs -0.056 mean for its non-degenerate folds).
  - Fix: the argmax is restricted to finite thresholds
    (`np.where(np.isfinite(thresholds), tpr - fpr, -np.inf)`); two regression
    tests cover it.
  - Impact bound, computed exactly from the saved per-fold taus: the bug
    fired on ≤3/100 folds per powered config (0 for photonic-fixed; the same
    fold 21 for every gate config), none of them catastrophic-collapse folds.
    Excluding every affected fold shifts means by ≤0.003 AUCPR and leaves all
    six configs significantly negative (p ≤ 0.038). Since a finite pre-fix
    tau implies max J > 0, the fix provably changes nothing on unaffected
    folds, so the exclusion bound is exact and the 6-config re-run is
    unnecessary. (A confirmatory post-fix gate A/B was started and stopped
    once the analytical bound made it redundant.)
  - Note: on 2026-09-01, after the post-fix gate re-run, the Youden's-J bug
    was judged the more likely dominant driver of the negative mean. The
    2026-09-02 bound shows it is not: the significant negative mean survives
    its removal.

### Open

- **Calibration floor / Platt-scaling instability.** Raising the temperature
  clamp floor from `1e-3` to `0.1` reduces but does not eliminate
  catastrophic per-fold AUCPR collapse: post-fix runs still show worst-fold
  drops of -0.28 to -0.36 AUCPR, one of which sits exactly on the new `0.1`
  floor, and some collapse folds (classical backend) do not touch the floor
  at all, so a second mechanism is involved. Batch 1 and batch 2 powered runs
  used the old `1e-3` floor. A more principled fix (per-fold calibration
  sanity check, or a regularized/Bayesian temperature prior instead of a hard
  floor) has not been attempted.
- **Unresolved ~0.08 absolute AUCPR/AP gap** to the paper for both XGBoost and
  MoE, attributed mainly to unspecified XGBoost hyperparameters; tuned XGBoost
  closes part of it (n=100 baseline 0.7255 vs paper 0.78).
- **Table 1 latency magnitude gap** (GQC 3-10x faster vs the paper's
  542-1387x) is not root-caused; trying `lightning.qubit` for the GQC VQC is
  the obvious next test.
- **No QPU access**: Table 6 hardware timings (C3 hardware-latency part) are
  not reproduced. This is an access limitation, not a scientific refutation.
- **Earlier write-ups were stress-tested only at n=15.** The Youden's-J bug
  surfaced only in the n=100 runs; code review and qualitative sanity checks
  at n=15 did not exercise it often enough to reveal it.
